# PreySense v3.1.1

## CPU compatibility

Added the documented Core Ultra 200HX host-bridge IDs 7D2D and 7D2F alongside existing 7D1C support. These variants were previously rejected during CPU power-register discovery, which could produce "Could not find CPU power registers" before PL1/PL2 could be applied. MCHBAR decoding now uses the documented address bits for this family. Firmware locks and driver-access requirements still apply.

## Custom fan control: what the EC actually does

This release revises fan control based on offline decoding of the PHN16S-71 ZBJ-KQ EC 1.08 firmware. The findings below are verified for that image; they are not a universal contract for all Acer laptops.

### Custom percentage is additional cooling, not raw PWM

In the decoded firmware, entering Custom enables an EC-controlled RPM feedback path. A percentage command does not directly set PWM or request that percentage of maximum RPM. The EC calculates:

    targetRPM = factoryStageRPM + (maximumRPM - factoryStageRPM) × boostPercent / 100

The baseline comes from the EC's current factory stage. The maximum comes from the final slot of the loaded factory table. In the extracted variant-0 table those endpoints are CPU 6800 RPM and GPU 6400 RPM; the other table variant contains different endpoints. These are firmware targets, not measurements of the fans' physical limits.

At 0% boost, the target remains the current factory baseline: zero does not necessarily stop a fan. At 100%, the target reaches the table endpoint. Intermediate percentages use that fraction of the remaining headroom.

For example, with a CPU baseline of 1970 RPM and endpoint of 6800 RPM, a 40% boost produces a target of 3902 RPM. If the EC later selects a baseline of 3600 RPM, the same 40% request produces 4880 RPM. A changing speed therefore does not by itself prove that Custom was overwritten.

### The EC remains in charge of fan drive

The EC continues running its temperature-stage logic and comparing target RPM with tachometer feedback. It adjusts PWM to approach the target. Factory rising/falling thresholds, filtering, transition counters and additional firmware paths can affect the result. CPU and GPU have separate EC stage state; they are not guaranteed to advance together. The complete influence of each sensor on both internal stage paths has not been established.

The decoded Custom-enable commands also reset the corresponding stage. Re-entering Custom periodically is therefore not a harmless keepalive. PreySense sends changed boost requests rather than repeatedly reinitializing Custom for unchanged values.

### PreySense's curve controls boost requests

PreySense has its own software temperature curve that selects the boost percentage sent to the EC. That software curve is separate from the EC's factory RPM stages. New and reset curves start at 0% boost throughout; existing saved percentages are preserved.

Boost increases now take effect on the next shared temperature sample without Fan Control Delay. Decreases use a fixed 3°C hysteresis below the entry threshold to avoid alternating requests near a boundary. When synchronization is enabled, the software uses a shared stage and sends the higher request to both fans; this does not guarantee equal RPM or identical internal EC stages. With synchronization disabled, each software curve follows its own sensor, with CPU fallback when the GPU sensor is unavailable.

The estimate uses the selected point's temperature and the bundled reference curve, rounded to the nearest 100 RPM. Successful calibration selects hardware Max directly, waits for spin-up and measures both fans; those saved maxima then replace the reference endpoints in subsequent estimates. The baseline still comes from the bundled curve, so calibration does not turn the estimate into live EC feedback or verify another laptop's factory curve. No user firmware scanning or extraction is performed.

### Readback limitations

In the decoded firmware, the WMI behavior and speed getters return cached requests, not proof of effective EC ownership or measured fan RPM. Fan-command success also does not establish that the hardware retained the request. Auto explicitly releases Custom control, while a speed-only write does not reissue the Custom-enable command. PreySense does not treat RPM differences alone as grounds to fight the EC with repeated mode writes.

## Performance and reliability

- Move fan-setting, metrics and tuning saves off the UI thread and combine pending settings edits.
- Avoid cloning the entire configuration while dragging fan points.
- Await in-flight mode/tuning operations before disposing hardware at shutdown.
- Compress embedded keyboard layout data without removing device support, saving roughly 350 KB in the executable.
- Verify LCD Overdrive capability and state through firmware readback. This checks reported state, not a physical panel response-time measurement.
